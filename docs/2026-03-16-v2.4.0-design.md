# Design: Dev Pipeline v2.4.0 — Independent Verification, Notion Enforcement, Update Command

**Date:** 2026-03-16
**Status:** Approved
**Scope:** Both `dev-pipeline-backend` and `dev-pipeline-frontend` plugins + shared tools

---

## Problem Statement

Three gaps in the v2.3.0 pipeline:

1. **No independent verification.** When not using subagent-driven development, the builder and checker are the same entity. The requirements chain (requirements.md -> must_haves -> traceability) is well-designed but enforcement is prose instructions, not mechanical checks or independent agent audits.

2. **Notion integration silently fails.** Every phase says "warn but don't block," but if card creation fails at INTAKE, all downstream updates are skipped without any visible warning. The user loses track of features in the Kanban.

3. **Plugin updates are painful.** No `/dev:update` command exists. Updating requires manual plugin reinstallation through Claude's plugin commands, which is unclear and error-prone.

---

## Improvement 1: Independent Verification System

### Architecture

Two layers of verification, both respecting the "spec-driven" design:

```
BUILD:Review (per wave)
  |
  +-- Layer A: verify-must-haves (tool command, deterministic, ~2s)
  |     Checks: file existence, route existence, spec non-empty, anti-stub scan
  |
  +-- Layer B: Semantic verification agent (dispatched, independent, ~30-60s)
  |     Agent reads must_haves only + codebase. No build context.
  |     Backend: qa-expert | Frontend: code-reviewer
  |
VALIDATE:Execute (comprehensive)
  |
  +-- Layer C: Independent verifier agent (dispatched, clean context)
  |     Reads ALL requirements.md + ALL must_haves. Fresh agent, no build history.
  |     Backend: qa-expert + domain agents | Frontend: code-reviewer + domain agents
```

### Layer A: `verify-must-haves` Tool Command

New command in `dev-pipeline-tools.js`:

```bash
node dev-pipeline-tools.js verify-must-haves <feature-dir> --plugin backend --wave N
```

**Input:** Reads `waves/WAVE_NN.md` for `must_haves` section (truths, artifacts, key_links).

**Backend checks (`--plugin backend`):**
1. Every file in `must_haves.artifacts` exists on disk
2. Every route pattern in `must_haves.key_links` exists in `config/routes.rb`
3. Every spec file has at least one `it` or `describe` block (not empty)
4. Scan listed artifacts for `TODO|FIXME|raise NotImplementedError|placeholder`
5. Check that RSpec output is present in the wave's review artifact

**Frontend checks (`--plugin frontend`):**
1. Every file in `must_haves.artifacts` exists on disk
2. Every component/page in `must_haves.key_links` has a resolvable import path
3. Scan for `TODO|placeholder|() => {}|console.log` in listed artifacts
4. Check that type-check output is present in the wave's review artifact

**Output:** JSON with `pass/fail` per must_have category, specific `file:line` evidence for failures.

### Layer B: BUILD:Review Semantic Verification Agent

Dispatched AFTER Layer A passes. Receives ONLY:
- The wave's `must_haves` block
- Codebase access (Read, Grep, Glob)
- NO build artifacts, NO context from earlier stages

Prompt pattern: "You are verifying work you did NOT build. Here are the must_haves. Check each truth against the actual codebase. Report PASS/FAIL with file:line evidence."

| Pipeline | Agent | Focus |
|----------|-------|-------|
| Backend | `qa-expert` | API behaviors, data integrity, service wiring |
| Frontend | `code-reviewer` | Component rendering, state management, route guards |

### Layer C: VALIDATE Independent Verifier

Same pattern as Layer B but comprehensive. Dispatched in VALIDATE:Execute with:
- ALL `requirements.md` requirement IDs
- ALL wave `must_haves` blocks
- Codebase access only — no build context

| Pipeline | Primary Agent | Domain Agents (conditional on MANIFEST tags) |
|----------|--------------|----------------------------------------------|
| Backend | `qa-expert` | `rails-expert`, `security-engineer`, `performance-engineer` |
| Frontend | `code-reviewer` | `security-engineer`, `performance-analyzer`, `ui-designer`, `frontend-developer` |

## Improvement 2: Notion Retry + Loud Warning Protocol

### Design

Never silently skip Notion. Try harder, warn louder, but still don't block.

**At INTAKE (card creation):**
1. Try `mcp__plugin_Notion_notion__notion-create-pages`
2. If fail -> wait 2 seconds -> retry once
3. If retry fails -> display loud banner + persist warning in review artifact
4. Don't block pipeline

**At all downstream phases (status updates):**
1. Check MANIFEST for Card ID
2. If missing -> display loud warning EVERY TIME (never silently skip) + persist in artifact
3. If present -> try update -> if fail -> retry once -> warn if still fails + persist in artifact
4. Continue pipeline regardless

### Warning Format (persisted in review artifacts)

```
## Notion Status
- WARNING: [Card not created | Update failed | Card ID missing in MANIFEST]
- Attempts: [1/2 or 2/2]
- Impact: Downstream Notion updates will be skipped
- Fix: Create card manually -> add Card ID to MANIFEST Notion Integration section
```

### Files Changed

| File | Change |
|------|--------|
| `shared/references/notion-integration.md` | New "Retry + Warning Protocol" section with the canonical pattern |
| Backend phase skills (intake, plan, document, build, validate, ship, pause) | Replace inline "warn but don't block" with reference to protocol |
| Frontend phase skills (intake, plan, design, document, build, validate, ship, pause) | Same replacement |

## Improvement 3: `/dev:update` Command

### How It Works

Source of truth: `~/.claude/plugins/marketplaces/thoven-dev/` (git repo: `Andresem611/dev-workflow.git`)
Runtime: `~/.claude/plugins/cache/thoven-dev/` (versioned snapshots)

```
/dev:update
  1. Read current version from plugin.json (2.3.0)
  2. git fetch on marketplace directory
  3. Compare local HEAD vs remote HEAD
  4. If same -> "Already up to date"
  5. Show: files changed, new/modified skills, CHANGELOG diff
  6. Ask user to confirm
  7. git pull
  8. Display: "Restart Claude Code to pick up changes"
```

### SessionStart Update Check (Optional)

Background hook that runs on session start:
1. `git fetch --dry-run` in marketplace directory
2. If behind remote -> write status to cache file
3. Session context hook reads cache, displays "Update available" banner

### Files Changed

| File | Change |
|------|--------|
| Both `commands/dev:update.md` | New update command (shared content, registered in both plugin.json) |
| Both `hooks/check-update.js` | New SessionStart hook for background update check |
| Both `plugin.json` | Add `dev:update` command entry, register new hook, bump version to 2.4.0 |
