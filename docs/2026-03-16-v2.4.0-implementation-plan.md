# Implementation Plan: Dev Pipeline v2.4.0

**Design Doc:** `docs/2026-03-16-v2.4.0-design.md`
**Target Version:** 2.4.0
**Plugin Root:** `~/.claude/plugins/marketplaces/thoven-dev/`

---

## Decision Log

| ID | Decision | Choice | WHY | Alternatives Rejected |
|----|----------|--------|-----|----------------------|
| D01 | Verification tool location | New command in existing `dev-pipeline-tools.js` | Single tool file already handles all pipeline validation; adding here keeps one entry point | Separate `verify-must-haves.js` file (extra dependency, inconsistent with existing pattern) |
| D02 | Notion retry mechanism | Inline retry in each skill via protocol reference | Each skill already has Notion blocks; replacing text is minimal. No shared JS needed. | Shared retry helper in JS (over-engineered for 2-second wait + 1 retry) |
| D03 | Update command scope | One command file shared by reference, registered in both plugin.json | Identical logic for both plugins; no pipeline-specific differences | Separate command per plugin (duplication) |
| D04 | SessionStart update hook | Single JS file copied to both plugins | Must run per-plugin like existing hooks | Shared hook (cache path resolution differs) |
| D05 | must_haves parser | Parse markdown `## must_haves` section with regex | Wave files use markdown, not YAML. Regex on `- **truths**:`, `- **artifacts**:`, `- **key_links**:` patterns | YAML parser (must_haves are markdown lists, not YAML despite template showing yaml block) |
| D06 | Verification agent isolation | `isolation: "worktree"` NOT used — agent gets Read/Grep/Glob only | Verification is read-only; worktree isolation is for write operations | Worktree isolation (unnecessary overhead for read-only verification) |

## Wave Plan

### Wave 1: Core Infrastructure (no dependencies)

**Tasks:** T01, T02
**Strategy:** Sequential (T02 depends on T01's must_haves parser)

#### T01: Add `verify-must-haves` command to dev-pipeline-tools.js
- **File:** `plugins/shared/tools/dev-pipeline-tools.js`
- **Duration:** 2 hours
- **What:** Add new CLI command that:
  1. Reads wave file from `waves/WAVE_NN.md`
  2. Parses `must_haves` section (truths, artifacts, key_links)
  3. Backend checks: file existence, route matching in `config/routes.rb`, spec non-empty, anti-stub scan
  4. Frontend checks: file existence, import resolution, anti-stub scan
  5. Outputs JSON with per-category pass/fail and file:line evidence
- **Acceptance Criteria:**
  - [ ] `node dev-pipeline-tools.js verify-must-haves <dir> --plugin backend --wave 1` runs without error
  - [ ] `node dev-pipeline-tools.js verify-must-haves <dir> --plugin frontend --wave 1` runs without error
  - [ ] Missing artifact files produce FAIL with specific path
  - [ ] Anti-stub patterns detected with file:line
  - [ ] Route check works for backend (parses routes.rb)
  - [ ] Output matches existing JSON format (valid, issues, warnings pattern)

#### T02: Add Notion retry + warning protocol to shared reference
- **File:** `plugins/shared/references/notion-integration.md`
- **Duration:** 30 minutes
- **What:** Add new section "Retry + Warning Protocol" defining:
  1. INTAKE retry pattern (try -> wait 2s -> retry -> loud warning)
  2. Downstream phase pattern (check Card ID -> try -> retry -> warn)
  3. Warning format template (persisted in artifacts)
  4. "Never silently skip" rule
- **Acceptance Criteria:**
  - [ ] Protocol section added after existing "Error Handling" section
  - [ ] Warning format template is copy-pasteable by skills
  - [ ] Both INTAKE (create) and downstream (update) patterns documented

## NOT in Scope

| Feature | Reason |
|---------|--------|
| Automatic cache refresh after git pull | Claude Code plugin cache is managed by the CLI; we can't programmatically refresh it. User must restart. |
| npm-based distribution (like GSD) | Overkill for a private plugin with one user. Git pull is simpler. |
| Blocking Notion gate | User explicitly requested "try harder but don't block" |
| Restructuring the requirements chain | The spec-driven flow (requirements.md -> must_haves -> traceability) is solid; we're adding enforcement, not redesigning |
| Frontend validate adding `qa-expert` | Frontend pipeline uses `code-reviewer` for this role per existing domain-agent-map |
| Shared inner-loop-reference.md changes | Verification is phase-specific, not a loop-level concern |
