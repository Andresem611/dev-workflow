# Testing Anti-Patterns Reference

Source: Doc 1 §4.4 check #4 + Teach Mode evidence + ANTI_PATTERNS.md AP-06.

This reference is loaded by DOCUMENT (when emitting wave files) and consumed by BUILD Layer 2 stub-scan. Findings are **WARN** severity (per O5 polish-tier blocking policy) — surfaces a warning the reviewer must acknowledge, but does not block the wave.

## Pattern catalog

Each pattern: `name`, `regex`, `severity`, `false-positive caveat`, `manual-override path`.

### AP-T1 — Mock of function-under-test

- **Name:** `vi-mock-of-fut`
- **Regex:** `vi\.mock\(['"](.*?)['"]\)`
- **Severity:** WARN
- **False-positive caveat:** Legitimately mocking third-party libraries (`vi.mock('@tanstack/react-query')`) is fine. The trip is when the mocked module is the function or component being implemented in the same wave (e.g., `vi.mock('@/lib/canvas-save')` inside `lib/canvas-save.test.ts`).
- **Detection:** grep `vi.mock(` and check whether the mocked path resolves to a file in the wave's must_haves bound paths.

  **Feasibility note:** path-resolution against the wave's must_haves bound paths is non-trivial. v4.6 BUILD Layer 2 implements a simplified check: any `vi.mock('@/lib/...')` or `vi.mock('./...')` (relative or src-aliased path) is flagged; `vi.mock('@third-party/...')` is treated as legitimate by convention. Reviewer ack required for project-internal mocks regardless. False-positive rate target: <5% of wave-test files.
- **Manual-override path:** add a comment in the test file: `// AP-T1-OVERRIDE: <reason>` (e.g., "third-party lib has runtime side-effects unsuitable for tests"). The override comment is appended to the wave's must_haves anti-pattern log.

### AP-T2 — Tautological assertion

- **Name:** `tautology`
- **Regex:** `expect\(true\)\.toBe\(true\)|expect\(1\)\.toBe\(1\)|expect\(['"]a['"]\)\.toBe\(['"]a['"]\)`
- **Severity:** WARN
- **False-positive caveat:** None. Tautological asserts always indicate a placeholder.
- **Manual-override path:** rewrite the test to assert against actual production behavior, OR add `// AP-T2-OVERRIDE: <reason>` if the tautology is documenting a known-impossible case.

### AP-T3 — Skipped test

- **Name:** `it-skip`
- **Regex:** `it\.skip\(|test\.skip\(|describe\.skip\(|xit\(|xtest\(`
- **Severity:** WARN
- **False-positive caveat:** Genuinely-skipped tests for environment-specific reasons (e.g., requires GPU) are valid. Trip is when the skip exists for "TODO" reasons.
- **Manual-override path:** add `// AP-T3-OVERRIDE: <reason>` (e.g., "skipped on CI: requires WebGL") OR fix and unskip.

### AP-T4 — Underscore-only assertion

- **Name:** `expect-underscore`
- **Regex:** `expect\(_\)`
- **Severity:** WARN
- **False-positive caveat:** None. `expect(_)` is unambiguously a placeholder.
- **Manual-override path:** rewrite the assertion against the actual value.

### AP-T5 — Snapshot-only test

- **Name:** `snapshot-only`
- **Regex:** `toMatchSnapshot\(\)` (alone, with no other assertions in the test body)
- **Severity:** WARN
- **False-positive caveat:** Snapshot tests are valid for stable rendered-output verification. Trip is when the test body has no other assertions and the snapshot was generated by the same test run that wrote the test.
- **Detection:** grep `toMatchSnapshot()` and confirm the same `it(...)` block has no other `expect(...)` calls.

  **Feasibility note:** AST-aware scoping for "alone in the test body" is not implemented in v4.6. Layer 2 falls back to a looser greppable form: any line containing only `toMatchSnapshot()` (modulo whitespace) is flagged. Reviewer determines whether the snapshot is the only assertion. AST tooling deferred to v5.0+.
- **Manual-override path:** add at least one assertion that exercises a behavior the snapshot wouldn't catch (e.g., `expect(result.length).toBeGreaterThan(0)`).

## Mode propagation

- Reduction: AP-T1 + AP-T2 + AP-T4 only (skip T3/T5 to keep noise low).
- Hold: all 5 patterns.
- Expansion: all 5 + manual reviewer skim of `tests/` directory for additional smell patterns.

## How BUILD consumes this

Layer 2 stub-scan (post-must_haves) greps the wave's added/modified test files for each regex. Per match:

1. Locate the file:line of the match.
2. Check for an inline `// AP-T<N>-OVERRIDE:` comment within 5 lines.
3. If override present: log to `<feature>/.dev/build/anti-pattern-overrides.log` and continue.
4. If no override: emit a WARN with the file:line and the pattern name. The reviewer must acknowledge.

## How DOCUMENT signals this

When DOCUMENT emits wave files, append a `## test-anti-patterns` block referencing this file. Example wave-file snippet:

```markdown
## test-anti-patterns

BUILD Layer 2 will scan this wave's tests for the patterns in
`references/testing-anti-patterns.md`. Findings are WARN severity. Reviewer
must acknowledge each finding before the wave passes Layer 2.
```

End of reference.
